# Часть 2. Текущие рекомендации

По состоянию на 2026-08-16, ревизия `a2f4a24`.

## 2.0. Общая оценка

Проект заметно выше среднего для личного инструмента: чистый доменный слой, pydantic-модели, детерминированная логика фильтрации и скоринга, 86 проходящих тестов без сетевых вызовов, продуманная политика «output — производные данные». Это хороший фундамент.

Основная проблема не в коде, а в **рассинхронизации между документацией и реальностью** — а именно это критично для агентной разработки. Плюс один блокирующий баг рантайма и несколько дыр в устойчивости.

| Область | Оценка |
|---|---|
| Доменная логика (normalize/filters/scoring/dedupe) | Хорошо |
| Слоение и границы модулей | Средне |
| Готовность к агентной разработке | **Плохо** |
| Безопасность | Средне-хорошо (локальный однопользовательский периметр держит) |
| Инструментарий (lint/types/CI/CHANGELOG) | **Отсутствует** |
| Тесты | Хорошо по покрытию сценариев, нет измерения coverage |

## 2.1. Архитектура

### Фактическая карта зависимостей

```
cli.py ──┬─> config.py ──> utils.py
         ├─> connectors/{headhunter,jooble,...} ──> filters.py
         ├─> capture.py ──┬─> linkedin_queue.py
         │                ├─> persistence.py ──> normalize/filters/scoring/deduplicate/export
         │                └─> export.py (output_paths)
         ├─> email_ingestion.py ──> connectors/headhunter.py
         ├─> linkedin_fetch.py ──> capture.py + connectors.headhunter._cheap_title_prefilter
         └─> sources.py, persistence.py, export.py
```

### Что работает хорошо

- Чистое ядро: `normalize.py`, `filters.py`, `scoring.py`, `deduplicate.py` — чистые функции над `NormalizedVacancy`, легко тестируются, без I/O.
- Конфиг как контракт: `config.py` с `extra="forbid"` на `Preferences` — опечатка в YAML падает сразу.
- Единая точка пересборки — `persistence.py:33` `rebuild_from_authoritative_sources` — вся деривация выходных файлов идёт через одну функцию.
- Инъекция зависимостей в тестируемых местах: `imap_factory`, `hh_lookup`, `page_fetcher`, `opener` — правильный приём.

### Архитектурные проблемы

**2.1.1. `export.py` выполняет роль реестра путей.**
`output_paths()` (`export.py:13`) импортируется из `capture`, `linkedin_queue`, `email_ingestion`, `persistence`. Модуль «экспорт» стал общей зависимостью всех остальных. Нужен отдельный `paths.py`, иначе любая правка экспорта рискует зацепить пол-проекта.

**2.1.2. `capture.py` смешивает три слоя.**
Транспорт (FastAPI, CORS, токен), доменную логику (дедуп LinkedIn, обновление очереди) и оркестрацию (полная пересборка выходов). `process_manual_capture` (`capture.py:71`) — 39 строк, делающих 6 разных вещей. Самая опасная точка правки в проекте.

**2.1.3. Диспетчеризация нормализации через утиную типизацию с catch-all.**
`normalize_record` (`normalize.py:70`) определяет источник по наличию ключей, и **любая нераспознанная запись молча уходит в `_normalize_himalayas_record`**. Если HH изменит форму ответа (пропадёт `area` или `employer`), записи не упадут с ошибкой — они тихо нормализуются как Himalayas и потеряют почти все поля. Нужен явный `__source` на всех записях и `raise` на неизвестном источнике.

**2.1.4. Перекрёстный импорт приватного API.**
`linkedin_fetch.py:14` импортирует `_cheap_title_prefilter` из `connectors.headhunter`. Функция не имеет отношения к HH — это общий предфильтр, ему место в `filters.py`.

**2.1.5. Нет инкрементальности.**
Каждый захват вакансии из расширения запускает полную ренормализацию всех записей и перезапись всех 10+ выходных файлов (`capture.py:84`). Плюс `manual_imports.json` читается целиком → append → перезапись: O(n²) по числу захватов.

**2.1.6. Мёртвый код и неиспользуемая конфигурация.**

| Объект | Статус |
|---|---|
| `export.py:70` `rebuild_exports()` | не вызывается нигде |
| `language.py:23` `is_international_english()` | не вызывается |
| `cli.py:385` `_fetch_all_sources(preferences)` | игнорирует аргумент, всегда `["headhunter"]` |
| `cli.py:389` `_source_key` | пустой словарь `aliases = {}` |
| `sources.py:51` `configured_search_count` | всегда 0, но выводится в таблицу |
| `pandas` в `pyproject.toml:11` | ноль использований в коде |
| `future_llm`, `citizenship_patterns`, `remote_allowed`, `timezone_filter_enabled`, `international_english_bonus`, `excluded_target_titles`, `source_quality_file` | валидируются, но не влияют ни на что |

Для агентной разработки это ложные сигналы: агент увидит `citizenship_patterns` в конфиге и решит, что фильтр по гражданству настраивается конфигом, — а он захардкожен в `filters.py:11`.

## 2.2. Готовность к агентной разработке

### 2.2.1. Документация противоречит коду (критично)

В репозитории **пять** источников правды, и они конфликтуют:

| Файл | Что утверждает |
|---|---|
| `README.md:12` | «No Playwright, browser login, browser profile... is part of the active project» |
| `job-assistant-chat-handoff.md:14` | «Do not restore Playwright logic, browser login, browser profiles, auth state» |
| `job-assistant-chat-handoff.md:40` | «Do not automate LinkedIn» |
| `specs/phase3_hybrid_ingestion.md:15` | то же самое |
| **`src/job_assistant/linkedin_fetch.py`** (287 строк) | **Playwright, persistent Chromium profile, `run_login()`, автоматический обход вакансий, детекция CAPTCHA** |
| `cli.py:234` | команда `linkedin-fetch --login` присутствует в CLI |
| `pyproject.toml:12` | `playwright` — жёсткая зависимость |

Плюс `opencode_first_vertical_slice.md` — 663 строки в корне, описывающие полностью устаревший scope (Himalayas-only, «Do not implement LinkedIn access»), и `specs/archive/` на 843 строки.

**Последствие:** любой агент, начавший с README или handoff, будет уверен, что Playwright-кода нет, и либо удалит его как «восстановленный запрещённый scope», либо напишет параллельную реализацию. Агент, начавший с `opencode_first_vertical_slice.md`, начнёт реализовывать Himalayas.

Это нужно разрешить **решением, а не документацией**: либо `linkedin_fetch.py` удаляется вместе с зависимостью `playwright` и командой CLI, либо спецификации переписываются так, чтобы автоматизация LinkedIn была явно разрешённым (и осознанно рискованным) режимом.

### 2.2.2. Нет `CLAUDE.md` / `AGENTS.md`

Ни одного файла инструкций для агента. Всё, что агент должен знать — инварианты персистентности, запрет живых запросов в тестах, `uv run` вместо `python`, команда прогона тестов — разбросано по трём markdown-файлам с разной степенью актуальности.

### 2.2.3. Нет `CHANGELOG.md`

*Статус: создан 2026-08-16.* Версия зафиксирована как `0.1.0`, история — один коммит `Initial commit`.

### 2.2.4. Стиль кода враждебен точечному редактированию

**117 строк длиннее 120 символов**, включая:

- `export.py:101` — 475 символов (список полей CSV)
- `normalize.py:285` — 639 символов (весь `_normalize_lever_record` в одной строке)
- `cli.py:172` — 411 символов
- `cli.py:110` — 391 символ (сигнатура `email_sync`)

Однострочные функции по 500+ символов: агент не может сделать точечную правку без переписывания всей строки, а diff становится нечитаемым для ревью. Самая дешёвая в исправлении и самая ощутимая по эффекту проблема.

### 2.2.5. Нет ни линтера, ни типизации, ни CI

Отсутствуют: `ruff`, `mypy`/`pyright`, `.pre-commit-config.yaml`, `.github/workflows/`, `py.typed`, измерение coverage. Единственный контроль качества — `pytest`. Агент не может проверить свою работу ничем, кроме тестов, и не получит обратной связи по типам при том, что весь код аннотирован.

`.pytest_cache/` отсутствует в `.gitignore` — сейчас не отслеживается только по случайности.

### 2.2.6. Нет `.env.example`

Переменные `EMAIL_IMAP_*`, `HH_ACCESS_TOKEN`, `HH_USER_AGENT`, `JOOBLE_API_KEY` описаны только прозой в README. Агент не может настроить окружение без чтения исходников.

### Что сделано правильно

- Capture-сервер слушает только `127.0.0.1`, требует токен, сравнение через `secrets.compare_digest` (`capture.py:60`) — таймингов не течёт.
- CORS по умолчанию с пустым `allow_origins` (`capture.py:55`) — кросс-доменный preflight не пройдёт.
- Расширение имеет минимальные права: `activeTab`, `scripting`, `storage`, host_permissions только на localhost. Manifest V3.
- Строгая валидация payload через pydantic с лимитами длины и проверкой схемы URL.
- IMAP: только `readonly=True` и `BODY.PEEK[]`, никаких мутаций. `IMAP4_SSL` в Python 3.12 проверяет сертификаты по умолчанию.
- Whitelist URL из писем: только `/jobs/view/<id>` LinkedIn и `/vacancy/<id>` HH (`email_ingestion.py:170`) — произвольные ссылки не открываются.
- `open_url_default_browser` использует list-форму `subprocess.run` без `shell=True`, а URL предварительно валидируется регуляркой `^https://www\.linkedin\.com/jobs/view/(\d+)$`.
- Секреты не в git, `.env` и `data/capture_token` в `.gitignore`.

### Находки

**S1 — CSV injection (средний).**
`export.py:100-113` пишет `title`, `company` и производные описания напрямую в CSV. Вакансия с названием `=cmd|'/c calc'!A1` или `@SUM(...)` выполнится как формула при открытии в Excel/LibreOffice. Данные приходят из недоверенного источника (HH API, произвольная веб-страница через расширение). Фикс: префиксовать `'` для значений, начинающихся с `=`, `+`, `-`, `@`, таба или CR.

**S2 — Несанитизированные ошибки попадают в файлы (средний).**
`_safe_error_detail` (`cli.py:319`) вырезает токены, но применяется **только при выводе в консоль**. В `run_summary.json` (`export.py:64`) и `source_status.json` (`sources.py:102`) ошибки пишутся сырыми. При этом `connectors/headhunter.py:157` кладёт в текст ошибки `response_body={body[:500]}`. Санитизацию нужно перенести в точку создания сообщения, а не печати.

**S3 — Токен захвата не защищён на Windows (низкий-средний).**
`capture.py:48` — `TOKEN_PATH.chmod(0o600)` на Windows фактически no-op (меняется только флаг read-only). Файл читаем любым процессом пользователя. Учитывая, что проект работает на Windows 11, стоит либо использовать `icacls`, либо явно задокументировать это как принятый риск локального периметра.

**S4 — Молчаливая ротация токена (низкий).**
`get_or_create_token()` (`capture.py:42`) вызывается **на каждом запросе**. Если `data/capture_token` удалить при работающем сервере, следующий запрос сгенерирует новый токен и вернёт 401 без объяснения. Токен нужно читать один раз при старте.

**S5 — Нет проверки Host-заголовка (низкий).**
Защиты от DNS rebinding нет. Эксплуатация упирается в незнание токена, но `TrustedHostMiddleware` с `127.0.0.1`/`localhost` — одна строка.

**S6 — Persistent Chromium-профиль с сессией LinkedIn.**
`linkedin_fetch.py:18` — `data/browser_profiles/linkedin` хранит живые cookies LinkedIn на диске. Каталог в `.gitignore`, но это реальное хранилище учётных данных. Плюс автоматизация LinkedIn нарушает их ToS и грозит блокировкой аккаунта — что и указано в собственных спецификациях проекта как причина запрета.

**S7 — Источник `email` не проходит проверку учётных данных.**
В `config/preferences.yaml:71` у источника `email` не задан `requires_env`, поэтому `sources.py:42` рапортует `credential_status = "not_required"`. Команда `sources` показывает, что учётные данные не нужны, хотя без них `email-sync` падает.

**S8 — Markdown-инъекция в shortlist (низкий).**
Названия вакансий подставляются в `## {title}` без экранирования (`export.py:120`). Локальный файл, риск минимален, но ломает структуру отчёта.

## 2.4. Баги

**B1 — `capture-server` не запускается вообще (блокирующий).**
`capture.py:113` делает `import uvicorn`, но `uvicorn` отсутствует и в `pyproject.toml`, и в `uv.lock`, и в `.venv`. Проверено:

```
ModuleNotFoundError: No module named 'uvicorn'
```

Единственный поддерживаемый путь захвата LinkedIn — команда из README — падает. Тесты этого не ловят, потому что используют `TestClient`, минуя uvicorn. Фикс: добавить `uvicorn>=0.30` (или `fastapi[standard]`) в зависимости.

**B2 — `fetch-all` игнорирует `sources.email.enabled`.**
`cli.py:86-98` вызывает `sync_email_alerts` безусловно. Выставление `email.enabled: false` в конфиге ни на что не влияет — почта всё равно синхронизируется.

**B3 — Изоляция ошибок в `fetch-all` не работает для IMAP.**
Там же ловится только `RuntimeError`. Но `imaplib.IMAP4.error` наследуется напрямую от `Exception` (проверено), как и `ssl.SSLError`, `socket.gaierror`. Ошибка логина в почту роняет всю команду **после** успешной выкачки HeadHunter — результаты теряются. Docstring обещает «error isolation». То же в `cli.py:115` для `email-sync`.

**B4 — Гонка и потеря данных при записи JSON.**
`write_json` (`utils.py:30`) не атомарен — в отличие от `write_queue` (`linkedin_queue.py:55`), который сделан правильно через temp + replace. При этом `capture.py:74-83` — классический read-modify-write, а эндпоинт объявлен как `def` (не `async def`), значит FastAPI выполняет его в пуле потоков: два одновременных захвата дают потерянное обновление. Падение посреди записи оставляет битый `manual_imports.json`.

**B5 — Битый JSON роняет все команды.**
`read_json` (`utils.py:35`) не обрабатывает `JSONDecodeError`. `load_statuses` читает `source_status.json` на старте почти каждой команды (`sources.py:33`) — один повреждённый файл (см. B4) блокирует весь CLI, включая `validate-config`. Механизма восстановления нет.

**B6 — Учётные данные почты нельзя задать через переменные окружения.**
`email_ingestion.py:123-124` читает `EMAIL_IMAP_USER`/`EMAIL_IMAP_APP_PASSWORD` **только** из `dotenv_values(.env)`, тогда как host/port/mailbox строкой выше проверяют `os.getenv` первым. Судя по спецификации, это намеренно, но делает невозможным запуск в CI/контейнере и противоречит `env.py`, который и так загружает `.env` в окружение.

**B7 — Ложное срабатывание классификатора LinkedIn.**
`linkedin_fetch.py:76`:

```python
if "/login" in lowered or "sign in" in lowered and "linkedin" in lowered or "join linkedin" in lowered:
```

Смешаны `and`/`or` без скобок. По приоритету это `("/login" in x) or ("sign in" in x and "linkedin" in x) or ("join linkedin" in x)`. Работает почти как задумано, но `lowered` включает URL целиком, а любая страница вакансии LinkedIn содержит «sign in» в футере → нормальная страница классифицируется как `login_required`, и, поскольку это `STOP_REASON`, **прерывает весь прогон**. Нужны явные скобки и проверка по более специфичным маркерам.
